# 締切登録支援 設計ディスカッションまとめ

日付: 2026-08-10

この文書は、`docs/design_workflow.md` の「締切登録支援」を具体化するために行った議論の整理である。

レビュー結果と追加議論を反映し、v0.2 の締切登録支援について現時点の方針をまとめる。

---

## 0. 締切データの正本と Thunderbird への提供方法

v0.2 では、**締切データの正本は SQLite とする。**

Thunderbird には、SQLite の締切データから生成した iCalendar (`.ics`) を読み取り専用で購読させる。

`.ics` 内では各締切を `VTODO` として表現する。

概念的な構成は次のとおり。

```text
メール
  ↓
WorkInBox
  ↓
SQLite  ← 締切データの正本
  ↓
read-only deadlines.ics
  ↓
Thunderbird
```

重要な原則:

- 締切の追加・修正・削除は WorkInBox で行う。
- Thunderbird は `.ics` を購読し、締切を閲覧する。
- Thunderbird 側からの VTODO 編集・完了操作を WorkInBox へ逆同期することは v0.2 では行わない。
- `.ics` は SQLite から再生成できる派生データである。
- CalDAV は v0.2 では導入しない。
- 将来、Thunderbird 側からの編集や完了操作を WorkInBox に反映したくなった場合に、CalDAV 等の双方向方式を改めて検討する。

したがって、`締切登録済み` は「VTODO ファイルへの書き込み成功」ではなく、**WorkInBox の SQLite に締切を正式登録できたこと**を基準に扱う。

---

## 1. WorkInBox と Thunderbird の責務分担

WorkInBox は TODO アプリそのものにはしない。

### WorkInBox

- メールから締切があることを発見する。
- AI により締切候補を抽出する。
- AI が抽出できなかった締切を利用者が補完できるようにする。
- 1 通のメールから複数の締切候補を扱う。
- 利用者が締切候補を確認、修正、却下、登録できるようにする。
- 確定した締切を SQLite に保存する。
- SQLite の締切から読み取り専用 `.ics` / `VTODO` を生成する。
- 元メールと締切の関係を保持する。

### Thunderbird

- WorkInBox が提供する `.ics` を購読する。
- 締切をカレンダー / タスク UI で閲覧する。
- 元メールの閲覧、返信、アーカイブ等を行う。

v0.2 では Thunderbird 側で WorkInBox 由来の締切を編集する運用は前提としない。

WorkInBox が「今日やること」「優先順位」「進捗率」「プロジェクトボード」などまで管理し始めると独自の TODO / プロジェクト管理アプリになるため、その領域には踏み込まない。

---

## 2. 1 通のメールに複数の締切が存在することを前提とする

1 通のメールに 1 件だけ締切があるとは限らない。

例:

- エントリー締切: 8 月 20 日
- 論文投稿締切: 9 月 15 日
- 最終版提出締切: 10 月 3 日

したがって、AI の締切抽出結果は単一値ではなく、0 件以上の締切候補の配列として扱う。

概念例:

```json
{
  "deadlines": [
    {
      "title": "エントリー締切",
      "due": "2026-08-20",
      "source_text": "エントリー締切：8月20日"
    },
    {
      "title": "論文投稿締切",
      "due": "2026-09-15",
      "source_text": "論文投稿締切：9月15日"
    }
  ]
}
```

同じ日付でも意味が異なる締切は別候補として扱う。

一方、本文中で同じ締切が繰り返されている場合は、同一候補を重複登録しないようにする。

---

## 3. AI が締切日を抽出できない場合も候補として残す

AI が「締切が存在する」ことは判断できても、具体的な日付を抽出できない場合がある。

例:

> 提出期限については別紙を参照してください。

この場合、候補そのものを捨てず、日付未確定として利用者へ提示する。

```json
{
  "title": "提出期限",
  "due": null,
  "source_text": "提出期限については別紙を参照してください。"
}
```

利用者は Thunderbird で本文・添付等を確認し、WorkInBox で日付を入力できるようにする。

AI は入力支援であり、AI が日付を抽出できなかったことを理由に締切候補を失わないことを重視する。

---

## 4. 締切候補に対する基本操作

AI が抽出した各締切候補について、利用者は少なくとも次の 3 操作を行えるようにする。

### 登録しない

その候補は登録対象ではないと判断する。

候補単位の却下であり、他に有効な締切候補がある場合はメール全体の `締切あり` を削除しない。

### 修正する

候補のタイトル、日付、時刻等を修正する。

修正終了後は、修正後の候補を再度確認できる提示画面へ戻る。

修正しただけでは正式登録しない。

### 登録する

提示されている内容を WorkInBox の正式な締切として SQLite に保存する。

SQLite への保存に成功した候補を登録済みとする。

`.ics` / VTODO は SQLite の内容から生成されるため、個々の登録操作で `.ics` を正本として更新する考え方は採らない。

---

## 5. 利用者主導で締切を追加できるようにする

AI がすべての締切を発見できるとは限らない。

また、メールに明記されていなくても、利用者が業務上必要と判断するマイルストーンが後から生じることがある。

そのため締切登録支援画面には、例えば次の操作を設ける。

```text
＋ 締切を追加
```

例:

AI が抽出した締切:

- 論文投稿締切 9/15

利用者が追加する締切:

- 共著者へ初稿送付 8/30
- 図表確定 9/5

v0.2 では追加した締切も、起点となった Message-ID に関連付けて SQLite に保存する。

---

## 6. `締切登録済み` を付けるタイミング

1 通のメールから複数の締切候補が生じるため、1 件の締切を登録しただけで `締切登録済み` を付けてはいけない。

作業中の候補ごとに、例えば次の状態を持つ。

- `pending`: 未判断
- `registered`: SQLite に正式登録済み
- `rejected`: 登録しないと判断済み

例:

```text
エントリー締切   registered
論文投稿締切     registered
最終版提出       rejected
```

すべての候補について利用者の判断が完了した時点で、そのメールに対する締切登録支援が完了したと判断する。

### 1 件以上登録した場合

- `締切あり` は残す。
- `締切登録済み` を自動付与する。

`締切登録済み` は「そのメールについて必要な締切登録支援を完了した」という意味とする。

### 全候補を登録しなかった場合

利用者が最終的に、そのメールには登録すべき締切が存在しないと判断した場合は、

- `締切あり` を削除する。
- `締切登録済み` は付けない。

候補 1 件を `登録しない` としただけでは `締切あり` を削除しない。

---

## 7. SQLite に保持する情報

SQLite は締切データの正本である。

ただし、AI が出した未確定候補と、利用者が正式登録した締切は区別する。

### 作業中の候補

利用者が途中まで処理した状態を保持し、画面を閉じても再開できるよう、締切候補を SQLite に一時保存する。

概念例:

```text
deadline_candidates
- id
- source_message_id
- title
- due_at
- source_text
- status          # pending / registered / rejected
- created_by      # ai / user
- needs_review
```

すべての候補について判断が終わった後、不要な `pending` / `rejected` 作業データは整理・削除してよい。

### 正式登録された締切

正式登録された締切は SQLite に長期保持する。

概念例:

```text
deadlines
- id
- source_message_id
- title
- due_at
- timezone
- description
- created_by      # ai / user
- created_at
- updated_at
```

将来 Context を導入する場合は、ここに `context_id` 等を追加できるようにする。

---

## 8. v0.2 の関連単位は Message-ID とする

メールスレッドが進行すると、同じ業務文脈の締切が別メールへ分散する問題がある。

しかし v0.2 では、メールスレッド単位の Context は導入しない。

まずは **Message-ID 単位**で、締切と起点メールを関連付ける。

Context は v0.2 以後の拡張として検討する。

将来の Context 自動関連付け候補としては、以下を利用できる。

- `Message-ID`
- `In-Reply-To`
- `References`

件名だけを Context の識別キーにすることは避ける。

---

## 9. 関連する締切一覧は v0.2 以後に検討する

将来的には、同じメールスレッドや関連 Context から生じた締切を WorkInBox で一覧できることが望ましい。

例:

```text
関連する締切
--------------------------------
8/20  エントリー締切
9/15  論文投稿締切
10/3  最終版提出

＋ 締切を追加
```

ただし、Context を伴う「関連する締切一覧」は v0.2 の締切登録支援には含めず、後続バージョンで開発する。

v0.2 では、対象メールの Message-ID に直接関連付いた締切だけを扱えばよい。

## 10. ICS / VTODO に保持する WorkInBox 情報

`.ics` は SQLite から生成する読み取り専用の派生データである。

WorkInBox から生成した VTODO であることが分かるよう、共通カテゴリを付ける。

```text
CATEGORIES:WorkInBox,WIB-Deadline
```

元メールを後から探しやすいよう、`DESCRIPTION` に人間向けの出典情報を入れる。

推奨形式:

```text
--- WorkInBox Source ---
Message-ID: <abc123@example.com>
Mail-Date: 2026-08-10T08:30:00+09:00
From: sender@example.com
Subject: ○○学会 論文募集
```

さらに機械可読な情報として、次のカスタムプロパティを付けることを候補とする。

```text
X-WORKINBOX-DEADLINE-ID:123
X-WORKINBOX-MESSAGE-ID:<abc123@example.com>
X-WORKINBOX-MAIL-DATE:2026-08-10T08:30:00+09:00
```

役割:

- `UID`: VTODO の安定識別子。SQLite の deadline id から安定生成する。
- `X-WORKINBOX-DEADLINE-ID`: SQLite 上の締切との対応確認用。
- `DESCRIPTION`: 利用者が元メールを探すため。
- `X-WORKINBOX-*`: デバッグや将来の移行・再構築を補助するため。

SQLite が正本なので、これらのプロパティから通常運用時に SQLite へ逆同期する必要はない。

---

## 11. 日付・時刻の扱い

締切は単純な日付だけとは限らない。

例:

- 8 月 20 日
- 8 月 20 日 17:00
- 8 月 20 日中
- 日本時間 17:00
- Anywhere on Earth (AoE)

現時点の方針:

- メールに日付だけが記載されている場合は日付締切として扱う。
- メールに時刻が明記されている場合は時刻まで保持する。
- タイムゾーンは設定値を基本とする。通常は JST を想定する。
- メール本文に明示的なタイムゾーンがある場合の扱いは実装時に詰める。
- 年が省略されている場合は、メール送信日時以後に到来する最初の該当日付として補完する。
- AI による推定は利用者が確認・修正できることを前提とする。
- 推定の確信度が低い場合は `要確認` を表示して、利用者による確認を促す。
- 締切日時は「その時点までに作業を終える必要がある日時」を表す。

---

## 12. 重複登録と ICS 再生成

通常同期や AI の再実行によって、同一メールから同じ締切が重複登録されないようにする必要がある。

重複防止は SQLite の正式締切データを基準に行う。

`.ics` / VTODO は SQLite から何度でも再生成できるため、ICS 側に独立した登録状態を持たせない。

各正式締切には安定した内部 ID を持たせ、その ID から VTODO の `UID` を安定生成する。

例:

```text
UID:wib-deadline-123@workinbox
```

同じ SQLite 行から再生成する限り同じ UID になるようにする。

Thunderbird 側での編集内容を WorkInBox に取り込むことは v0.2 の対象外である。

---

## 13. Thunderbird のメールスレッドとの関係

利用者はメールを月単位でアーカイブしている。

WorkInBox 自身が完全なメールスレッド閲覧 UI を構築する必要はない。

将来的な Context 関連付けには `Message-ID`、`In-Reply-To`、`References` を利用できるが、v0.2 の締切登録では Message-ID 単位に留める。

詳細なメール確認は Thunderbird に委ねる。

## 14. v0.2 の締切登録支援ワークフロー

```text
締切ありメール
    ↓
AI が 0〜複数の締切候補を抽出
    ↓
作業中候補として SQLite に保存
    ↓
候補を利用者へ提示

候補ごとに:
    ├─ 登録しない → rejected
    ├─ 修正する   → 修正後に再提示
    └─ 登録する   → SQLite の deadlines に正式保存 → registered

必要なら:
    └─ ＋ 締切を追加 → user-created candidate

    ↓
全候補について判断完了
    ↓
1 件以上 registered
    ├─ Yes → 締切登録済み を自動付与
    │         締切あり は残す
    └─ No  → 締切あり を削除
              締切登録済み は付けない
    ↓
不要な候補作業データを整理
    ↓
SQLite の正式締切から read-only .ics / VTODO を生成
    ↓
Thunderbird が購読して表示
```

## 15. WorkInBox が TODO アプリ化しないための境界

WorkInBox が担当する範囲:

- メールから締切を発見する。
- 締切候補を抽出・補完する。
- 利用者が候補を確認・修正・却下する。
- 正式な締切を SQLite に保存する。
- 対象メールから利用者が締切を追加・修正できるようにする。
- SQLite から読み取り専用 ICS / VTODO を生成する。
- 元メールと締切の関連を保持する。

v0.2 では扱わない範囲:

- Thunderbird からの締切編集を WorkInBox へ逆同期する。
- CalDAV サーバ機能。
- Context 単位の関連締切一覧。
- 全タスク横断のプロジェクト管理。
- 進捗率やカンバン等の案件管理。

Thunderbird は WorkInBox が登録した締切を閲覧する既存 UI として利用し、WorkInBox はメールから締切を整理・登録するシステムとしての役割を保つ。

## 16. レビュー結果として確定した点

1. `締切登録済み` は「1 件以上登録し、すべての候補について判断済み」の場合に付ける。
2. 全候補を却下した場合は `締切あり` を削除し、`締切登録済み` は付けない。
3. `pending / registered / rejected` は締切登録支援の作業状態として扱い、処理完了後に不要な候補情報は整理・削除してよい。
4. 正式登録された締切と元メールの関係は SQLite に長期保持する。
5. v0.2 は Message-ID 単位で開始し、Context は後から拡張する。
6. Context 単位の「関連する締切一覧」は v0.2 以後の開発とする。
7. 締切日時は SQLite を正本とし、ICS / VTODO は派生表現とする。
8. Thunderbird は v0.2 では読み取り専用 `.ics` を購読する。
9. Thunderbird 側で編集された VTODO との双方向整合性は v0.2 では扱わない。
10. CalDAV は v0.2 では導入しない。

---

## 17. 現時点のまとめ

WorkInBox の締切登録支援は、「メール 1 通につき締切 1 件」という単純な処理ではなく、1 通のメールから生じる複数の締切候補を AI と利用者が整理し、正式な締切として SQLite に登録する機能とする。

SQLite が締切データの正本であり、Thunderbird には SQLite から生成した読み取り専用 `.ics` / `VTODO` を提供する。

v0.2 では Message-ID 単位の関連付けに留め、メールスレッドや案件をまとめる Context、関連締切一覧、CalDAV による双方向編集は後続バージョンで検討する。
