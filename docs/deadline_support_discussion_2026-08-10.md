## 0.　締め切りデータの取り扱い
- SQLite のデータを正本として、ica用のVTODOはそこから生成されるデータとする。
- Context の選び方をどうするか？（メールの件名？）

## 1. WorkInBox と Thunderbird の責務分担

WorkInBox は TODO アプリそのものにはしない。

締切についての責務は以下のように分ける。

### WorkInBox

- メールから締切があることを発見する。
- AI により締切候補を抽出する。
- AI が抽出できなかった締切を利用者が補完できるようにする。
- 1 通のメールから複数の締切候補を扱う。
- 利用者が締切候補を確認、修正、却下、登録できるようにする。
- メールやメールスレッドと、そこから生成された締切との関連を保持する。
- あるメールまたは関連する会話から生成された締切を一覧できるようにする。
- 作業中に新たに判明したマイルストーンを、利用者が締切として追加できるようにする。
- 確定した締切を Thunderbird の ToDo / VTODO として登録する。

### Thunderbird

- 登録済みの ToDo / VTODO を日常的に利用する。
- ToDo の完了管理を行う。
- カレンダーやタスク一覧として表示する。
- 必要に応じて登録後の締切内容を修正する。

WorkInBox が「今日やること」「優先順位」「進捗率」「プロジェクトボード」などを管理し始めると、独自の TODO / プロジェクト管理アプリになってしまうため、その領域には踏み込まない。

WorkInBox は、メールから生じた締切を Thunderbird の ToDo に送り出すまでの支援と、その出自・関連情報の保持を担当する。

## 2. 1 通のメールに複数の締切が存在することを前提とする

1 通のメールに 1 件だけ締切があるとは限らない。

例:

- エントリー締切: 8 月 20 日
- 論文投稿締切: 9 月 15 日
- 最終版提出締切: 10 月 3 日

したがって、AI の締切抽出結果は単一の締切ではなく、0 件以上の締切候補の配列として扱う。

概念例:

```json
{
  "deadlines": [
    {
      "title": "エントリー締切",
      "due": "2026-08-20",
      "source_text": "エントリー締切：8月20日"
    },
    {
      "title": "論文投稿締切",
      "due": "2026-09-15",
      "source_text": "論文投稿締切：9月15日"
    }
  ]
}
```

同一日付であっても意味が異なる締切は別候補として扱う。

一方、本文中で同じ締切が繰り返し記載されている場合は、重複候補をそのまま複数登録しないようにする必要がある。

---

## 3. AI が締切日は抽出できない場合も候補として残す

AI が「締切が存在する」ことは判断できても、具体的な日付を抽出できないことがある。

例:

> 提出期限については別紙を参照してください。

この場合、締切候補そのものを捨てず、日付未確定の候補として利用者に提示する。

概念例:

```json
{
  "title": "提出期限",
  "due": null,
  "source_text": "提出期限については別紙を参照してください。"
}
```

利用者は Thunderbird で添付や本文を確認し、必要な日付を WorkInBox に入力できるようにする。

AI は入力支援であり、AI が日付を抽出できなかったことを理由に締切候補を失わないことを重視する。

## 4. 締切候補に対する基本操作

AI が抽出した各締切候補について、利用者は少なくとも次の 3 操作を選択できるようにする。

### 登録しない

その締切候補は登録対象ではないと判断する。

候補単位の却下であり、他に有効な締切候補がある場合はメール全体の `締切あり` を削除しない。

### 修正する

候補のタイトル、日付、時刻などを修正する。

修正終了後は、修正後の候補を再度確認できる提示画面へ戻る。

修正しただけでは VTODO へ登録しない。

### 登録する

提示されている内容で ToDo / VTODO 登録を実行する。

登録に成功した候補は登録済みとして扱う。

登録処理に失敗した場合は、登録済みとして扱わない。

---

## 5. 利用者主導で締切を追加できるようにする

AI がすべての締切を発見できるとは限らない。

また、メールに明記されていないが、利用者が業務上必要と判断するマイルストーンが後から生じる場合もある。

そのため、締切登録支援画面には例えば次のような操作を設ける。

```text
＋ 締切を追加
```

例:

AI が抽出した締切:

- 論文投稿締切 9/15

利用者が追加する締切:

- 共著者へ初稿送付 8/30
- 図表確定 9/5

この追加機能は独立した TODO 作成機能ではなく、対象となるメールまたは関連する会話から生じたマイルストーンを Thunderbird へ登録するための機能と位置づける。

---

## 6. `締切登録済み` を付けるタイミング

1 通のメールから複数の締切候補が生じるため、1 件の VTODO 登録成功だけで `締切登録済み` を付けてはいけない。

候補ごとに、例えば次のような処理状態を持つ。

- `pending`: 未判断
- `registered`: 登録済み
- `rejected`: 登録しないと判断済み

例:

```text
エントリー締切   registered
論文投稿締切     registered
最終版提出       rejected
```

すべての候補について利用者の判断が完了した時点で、そのメールに対する締切登録支援が完了したと判断する。

### 1 件以上登録した場合

- `締切あり` は残す。
- `締切登録済み` を自動付与する。

`締切登録済み` は「そのメールについて必要な締切登録支援を完了した」という意味とする。

### 全候補を登録しなかった場合

利用者が最終的に、そのメールには登録すべき締切が存在しないと判断した場合は、

- `締切あり` を削除する。
- `締切登録済み` は付けない。

候補 1 件を `登録しない` としただけでは `締切あり` を削除しない。

## 7. SQLite に保持する情報

AI の抽出候補を永続的な TODO として SQLite に蓄積し続けることは避ける。

ただし、利用者が途中まで処理した状態を保持し、画面を閉じても作業を再開できるようにするため、締切登録支援中の候補は一時的に SQLite に保存することが望ましい。

概念的には次のような情報を保持する。

```text
deadline_candidates
- id
- source_message_id
- title
- due_at
- source_text
- status
- created_by       # ai / user
- vtodo_uid        # 登録後に必要なら保持
```

締切登録支援が完了した後は、AI 候補や rejected 候補など、作業用の一時データを整理・削除してよい。

一方、登録した VTODO と元メールの関連は、後から参照するため最低限残した方がよい。

例:

```text
deadline_links
- source_message_id
- vtodo_uid
- title_snapshot
```

重要な原則:

- 締切そのものの正本は Thunderbird / VTODO 側とする。
- SQLite は WorkInBox の作業状態と関連情報を保持する。
- WorkInBox が VTODO の完了状態や通常のタスク管理状態の正本にはならない。

## 8. メール単位だけではなく会話単位の関連が必要

締切を Message-ID 単位だけで関連付けると、メールスレッドが進行した際に関連締切が分散する。

例:

```text
Mail A
  → エントリー締切

Mail B (Mail A への返信)
  → 論文投稿締切

Mail C (Mail B への返信)
  → 最終版提出締切
```

これらは利用者から見ると同じ会話・業務文脈に属する締切である。

そのため WorkInBox 内部で、非常に薄い「関連コンテキスト」を持つことを検討する。

概念例:

```text
Context X
  ├─ Mail A
  ├─ Mail B
  ├─ Mail C
  └─ Deadlines
      ├─ エントリー締切
      ├─ 論文投稿締切
      └─ 最終版提出締切
```

自動的な関連付けには以下を利用できる。

- `Message-ID`
- `In-Reply-To`
- `References`

ただし、メールスレッドと実際の案件・業務単位は必ずしも一致しない。

そのため、まずは RFC 上の返信関係で自動的にまとめ、将来的に必要なら利用者が同一グループへの追加・移動を指示できる設計を検討する。

この Context は案件管理のためではなく、「関連するメールと締切をまとめて表示する」ための最小限の関連情報とする。

概念的な SQLite 構造例:

```text
contexts
- id

context_messages
- context_id
- message_id

deadline_links
- context_id
- source_message_id
- vtodo_uid
```

## 9. WorkInBox 上の「関連する締切」表示

WorkInBox でメールまたは関連コンテキストを見た際に、その文脈から生成された締切を一覧表示できることが望ましい。

例:

```text
関連する締切
--------------------------------
8/20  エントリー締切
9/15  論文投稿締切
10/3  最終版提出

＋ 締切を追加
```

これにより、メールスレッドが進行した後でも関連する締切を見失いにくくなる。

また、作業中に新たなマイルストーンが判明した場合、同じ関連コンテキストに新規締切を追加できる。

この一覧は「タスク管理画面」ではなく、あくまでメール・会話の文脈から生成された締切の関連表示と登録入口である。

## 10. VTODO に保持する WorkInBox 情報

WorkInBox から生成した ToDo / VTODO であることが分かるよう、共通カテゴリを付けることを検討する。

例:

```text
CATEGORIES:WorkInBox,WIB-Deadline
```

同じメールから複数の締切を生成する場合も、共通カテゴリを付けることで Thunderbird 側で整理しやすくする。

さらに、元メールを後から探しやすいように DESCRIPTION に WorkInBox 固有の出典情報を入れる。

例:

```text
--- WorkInBox Source ---
Message-ID: <abc123@example.com>
Mail-Date: 2026-08-10T08:30:00+09:00
From: sender@example.com
Subject: ○○学会 論文募集
```

人間向けの DESCRIPTION とは別に、WorkInBox が機械的に関連付けを確認できるよう、カスタムプロパティを持たせる案もある。

例:

```text
X-WORKINBOX-MESSAGE-ID:<abc123@example.com>
X-WORKINBOX-MAIL-DATE:2026-08-10T08:30:00+09:00
X-WORKINBOX-SOURCE-ID:...
```

考え方:

- DESCRIPTION: 利用者が読んで出典メールを確認するため。
- `X-WORKINBOX-*`: WorkInBox が機械的に関連を確認するため。

SQLite に関連情報を保持しつつ VTODO 側にも自己記述的な出典情報を残すことで、片方の情報だけに全面的に依存しない構成にする。

## 11. 日付・時刻について今後決める必要がある事項

締切は単純な日付だけとは限らない。

例:

- 8 月 20 日
- 8 月 20 日 17:00
- 8 月 20 日中
- 日本時間 17:00
- Anywhere on Earth (AoE)

また、メールでは年が省略される場合がある。

例:

```text
9月15日まで
```

- 日付の締め切りは必要であるが、メールに時刻情報の記載があるときは時刻まで含める。
- タイムゾーンは設定で定めたものとする。（通常はJST）
- 年が省略されている場合は、メール送信日時以後のその日付のとする。
- AI による推定は、利用者が確認・修正できることを前提とする。この時、確率が低い場合は 「要確認」のような掲示を行い、利用者の確認を促すようにする。
- 締切はいつの時点までに終わらせればならないのかの日時（時刻）とする。

## 12. 重複登録と登録後の変更

通常同期や AI の再実行によって、同一メールから同じ締切が重複登録されないようにする必要がある。

そのため、VTODO 登録時に生成された UID と元メール・締切との対応を WorkInBox 側で保持することを検討する。

また、登録後に利用者が Thunderbird 側で締切日時やタイトルを修正することも想定する。

v0.2 では登録後の編集そのものは Thunderbird に任せてもよいが、WorkInBox が登録済み VTODO を新規 VTODO と誤認して再生成しないことが必要である。

## 13. Thunderbird のメールスレッドとの関係

利用者はメールを月単位でアーカイブしている。

通常のフォルダ単位のスレッド表示ではメールが複数フォルダへ分散するが、Thunderbird の Conversation / Global Search を利用すれば複数フォルダにまたがる会話を参照できる可能性がある。

そのため WorkInBox がメール本文を独自にすべて複製し、完全なスレッド閲覧 UI を構築する必要はない。

WorkInBox は `Message-ID`、`In-Reply-To`、`References` などによる関連情報を持ち、詳細なメール確認は Thunderbird に委ねる方針が適している。

## 14. 現時点での締切登録支援ワークフロー案

```text
締切ありメール
    ↓
AI が 0〜複数の締切候補を抽出
    ↓
締切登録支援の作業状態として SQLite に保存
    ↓
候補を利用者へ提示

候補ごとに:
    ├─ 登録しない → rejected
    ├─ 修正する   → 修正後に再提示
    └─ 登録する   → VTODO 作成 → registered

必要なら:
    └─ ＋ 締切を追加 → user-created candidate

    ↓
全候補について判断完了
    ↓
1 件以上 registered
    ├─ Yes → 締切登録済み を自動付与
    │         締切あり は残す
    └─ No  → 締切あり を削除
              締切登録済み は付けない
    ↓
作業用候補データを整理
    ↓
登録した VTODO とメール / Context の関連だけ保持
```

## 15. WorkInBox が TODO アプリ化しないための境界

WorkInBox が担当する範囲:

- メールから締切を発見する。
- 締切候補を抽出・補完する。
- 利用者が候補を確認・修正・却下する。
- メールや会話に関連する締切を一覧する。
- その文脈から新しい締切を追加する。
- Thunderbird の VTODO へ登録する。
- 元メールと VTODO の関連を保持する。

原則として Thunderbird に任せる範囲:

- 全タスク横断の今日の TODO 一覧。
- タスクの優先順位管理。
- 日常的な完了操作。
- タスクのリマインダー運用。
- プロジェクト進捗率。
- カンバンなどの案件管理。

この境界を維持することで、WorkInBox は「メールから仕事を整理して既存の Thunderbird 環境へ橋渡しする」という当初の役割を保つ。

## 16. レビューで特に確認したい点

以下は、正式仕様へ反映する前に確認したい論点である。

1. `締切登録済み` は「1 件以上登録し、すべての候補について判断済み」の場合に付ける、でよいか。-> はい。
2. 全候補を却下した場合は `締切あり` を削除し、`締切登録済み` は付けない、でよいか。 -> はい。
3. 締切候補の `pending / registered / rejected` は作業中のみ SQLite に保持し、処理完了後は不要な候補情報を削除してよいか。-> はい。
4. 登録済み VTODO と元メールのリンク情報は SQLite に長期保持するか。-> はい。
5. メールスレッド単位の薄い `Context` を v0.2 から導入するか、それとも Message-ID 単位で開始して後から拡張するか。 -> Message-ID 単位で開始して後から拡張する。
6. WorkInBox 上の「関連する締切一覧」を v0.2 の締切登録支援に含めるか。 -> V0.2以後の開発とする。
7. VTODO の DESCRIPTION と `X-WORKINBOX-*` プロパティの具体的な形式。 -> 提案してほしい。
8. 日付のみ、時刻あり、タイムゾーン、年省略などの扱い。 -> 本文中を見てほしい。
9. Thunderbird 側で編集された登録済み VTODO と WorkInBox のリンク整合性をどこまで保証するか。-> 見なくてよいのでは？

## 17. 現時点のまとめ

WorkInBox の締切登録支援は「メール 1 通につき締切 1 件」という単純な処理ではなく、メールや会話から生まれる複数の締切・マイルストーンを利用者と AI が共同で整理し、Thunderbird の ToDo / VTODO へ登録するための支援機能として設計する。

ただし、登録後の日常的なタスク管理まで WorkInBox が担うことは避ける。

WorkInBox はメール・会話と締切の関係を把握し、Thunderbird は実際の ToDo を管理する、という分担を基本とする。
