# WorkInBox v0.2 設計メモ

## 1. 目的

Version 0.2 では、v0.1 で構築したメール追跡基盤を整理し、以下を実装する。

- 新規メール取り込み範囲の制限
- 既存メールの IMAP 状態同期
- active / inactive の追跡状態管理
- FastAPI による Web UI 基盤
- 作業分類のための IMAP タグ取り扱い基盤

AI による作業分類の具体的な仕様は、本書では未決定事項として扱う。

---

## 2. 基本方針

### 2.1 対象 mailbox

Version 0.2 では、設定された 1 つの mailbox のみを対象とする。

複数アカウント・複数 mailbox 対応は将来の改修対象とする。

### 2.2 内部利用 IMAP タグは使用しない

`WIB/Tracked` のような WorkInBox 内部管理専用の IMAP キーワードは使用しない。

IMAP はメールそのものの現在状態を保持し、WorkInBox 独自の追跡状態は SQLite 側で管理する。

そのため、SQLite を失った場合に過去の WorkInBox 管理状態を IMAP だけから完全復元することは保証しない。

### 2.3 作業タグの正本

利用者向けの作業タグは IMAP 上のタグを正本とする。

SQLite に作業タグを独立した正本として保持しない。

作業タグは複数同時に付与できる。

対象となる作業タグは以下とする。

- 締切あり
- スケジュール調整
- 回答必要
- 読む・検討

---

## 3. 新規メール取り込み

### 3.1 対象

新規に WorkInBox へ取り込むメールは、以下をすべて満たすものとする。

- 対象 mailbox 内に存在する
- スターが付いている
- 過去 N 日以内のメールである

`N` は設定値とする。

### 3.2 日付判定

過去 N 日の判定は日付単位とする。

厳密な時刻単位の境界判定は行わない。

基準となる日付情報は、IMAP SEARCH で扱いやすく、実装が単純になる方法を採用する。

### 3.3 過去 N 日条件の適用範囲

過去 N 日という条件は、新規メール探索時だけに使用する。

一度 SQLite に取り込まれたメールは、受信日が N 日より古くなっても、それだけを理由に inactive にはしない。

---

## 4. メール識別

### 4.1 IMAP 上の操作対象

IMAP 上の現在位置・操作対象の識別には、以下を使用する。

- mailbox
- UIDVALIDITY
- UID

### 4.2 論理的な同一メール判定

`Message-ID` は論理的な同一メール判定および重複登録防止に使用する。

新規探索で同じ `Message-ID` のレコードが既に SQLite に存在する場合、原則として新しいレコードは作成しない。

### 4.3 Version 0.2 で扱わないもの

UIDVALIDITY の変更や UID の変更に伴う高度な再同定・復旧処理は Version 0.2 の対象外とする。

これらは v0.2 以降の改修で検討する。

---

## 5. 追跡状態

### 5.1 tracking_status

追跡状態は enum とし、Version 0.2 では以下を使用する。

- `active`
- `inactive_unstarred`
- `inactive_moved`

### 5.2 active

通常処理の対象となる状態。

原則として以下を満たすメールが active である。

- 対象 mailbox 内に存在する
- スターが付いている

### 5.3 inactive_unstarred

対象 mailbox 内には存在するが、スターが外れたメール。

Thunderbird 側でスターを外した場合は、常に WorkInBox の追跡終了とみなし、`inactive_unstarred` にする。

WorkInBox 内の操作によるスター解除か、Thunderbird 等の外部操作によるスター解除かは区別しない。

### 5.4 inactive_moved

保存している UID が対象 mailbox 内に存在しなくなったメール。

Version 0.2 では、メールが別フォルダへ移動された場合と削除された場合を区別しない。

いずれも WorkInBox の通常処理対象ではなくなったものとして `inactive_moved` とする。

### 5.5 inactive 判定

正常な IMAP 応答の結果として状態変化を確認できた場合、1 回の同期で即座に inactive へ変更する。

複数回の確認や猶予期間は設けない。

### 5.6 active への復帰

inactive になったメールが再び対象 mailbox 内のスター付きメールとして検出された場合は `active` に復帰させる。

同じ `Message-ID` の既存レコードがある場合、新規レコードを作らず既存レコードを再利用する。

---

## 6. 状態日時

Version 0.2 では状態履歴テーブルは持たない。

現在状態と、その状態へ最後に変化した日時だけを保持する。

推奨項目:

- `tracking_status`
- `status_changed_at`
- `last_imap_checked_at`

`status_changed_at` は active / inactive のどちらへの変更でも更新する。

将来 inactive データを一定期間後に物理削除する場合にも、この日時を利用できる。

---

## 7. 同期処理

### 7.1 通常同期

通常同期では、SQLite 上の `active` メールを既存メール同期の対象とする。

処理順序は以下を基本とする。

1. 既存 active メールの IMAP 状態を確認する
2. 必要に応じて追跡状態を更新する
3. 過去 N 日のスター付きメールを新規探索する
4. 未登録メールを SQLite に追加する
5. DB 更新を確定する

### 7.2 全件再確認

FastAPI UI 上に通常同期とは別に「全件再確認」を設ける。

全件再確認では inactive を含む既存レコードも再確認対象とする。

再び対象 mailbox 内のスター付きメールとして確認できた場合は active に復帰させる。

### 7.3 部分失敗

特定メールの IMAP 取得・確認に失敗した場合は、以下とする。

- 当該メールの SQLite 上の状態は変更しない
- エラーを記録する
- 他メールの同期処理は継続する

### 7.4 IMAP 接続失敗

IMAP 接続、SEARCH、または mailbox 全体の確認自体が失敗した場合、その失敗を理由としてメールを inactive にしない。

SQLite 上の既存状態を維持する。

「正常な IMAP 応答でメールが存在しない」と「IMAP 処理そのものが失敗した」は明確に区別する。

---

## 8. Web UI

### 8.1 Version 0.2 の目的

Version 0.2 では、以後の WorkInBox 機能を載せるための Web UI 基盤を作る。

まずは表示機能を優先する。

### 8.2 技術構成

Version 0.2 の Web UI は以下の構成とする。

- FastAPI
- Jinja2
- サーバーサイド HTML レンダリング

Version 0.2 では React、Vue 等を利用した Single Page Application は採用しない。

HTMX も必須とはせず、まずは通常の HTTP リクエスト、フォーム送信、ページ再描画による単純な構成で実装する。

実運用後に部分更新の必要性が明確になった場合は、HTMX 等の追加を検討する。

### 8.3 技術選択の理由

Version 0.2 の主目的は、フロントエンド技術の高度化ではなく、以下を安定して利用できる状態にすることである。

- メール同期
- 追跡状態の確認
- active メール一覧
- inactive メールの確認
- 通常同期
- 全件再確認

Version 0.2 の画面要件では、ブラウザ側に複雑な状態管理を持つ必要がないため、SPA を導入しない。

必要な複雑さが明確になるまでは、構成を単純に保つ。

### 8.4 UI 層と業務ロジックの分離

FastAPI は WorkInBox 本体ではなく、WorkInBox の機能を利用するための UI 層として扱う。

FastAPI の route 関数へ IMAP 処理や SQLite の業務処理を直接実装しない。

構造は概ね以下とする。

```text
Browser
  |
  v
FastAPI / Jinja2
  |
  v
Application Service
  |        |
  v        v
IMAP     SQLite
```

同期、状態判定、メール取得などの業務ロジックは Application Service 等の UI 非依存層へ配置する。

これにより、将来以下の変更が必要になった場合でも業務ロジックを再利用できるようにする。

- HTMX の導入
- JSON API の追加
- React 等の SPA への変更
- CLI からの利用

### 8.5 通常一覧

通常の管理対象一覧には `active` メールのみ表示する。

最低限、以下を確認できるようにする。

- 件名
- 差出人
- 受信日時
- 現在の追跡状態
- IMAP 上の作業タグ

### 8.6 inactive メール

inactive メールは通常一覧には表示しない。

通常一覧とは別に inactive メールを確認できる画面を用意する。

Version 0.2 では、active と inactive の確認画面を明確に分離する。

### 8.7 同期操作

UI 上では以下を別操作として用意する。

- 通常同期
- 全件再確認

Version 0.2 では、UI 完成後は UI 上から同期を実行する運用を前提とする。

そのため、CLI と UI からの同時同期など、高度な排他制御は Version 0.2 の必須要件としない。

### 8.8 UI からの状態編集

Version 0.2 の初期段階では、`tracking_status` を UI から直接変更する機能は実装しない。

追跡状態は IMAP の状態確認結果から決定する。

---

## 9. データ削除

inactive になったメールは Version 0.2 では SQLite から物理削除しない。

将来、一定期間 inactive のレコードを削除・整理する仕組みを追加する。

削除ポリシーの具体的な期間・条件は Version 0.2 では決定しない。

---

## 10. AI 作業分類

AI による作業タグ分類は Version 0.2 のロードマップに含まれるが、具体的な仕様は別途議論して決定する。

現時点で確定している前提は以下のみとする。

- 作業タグは複数同時付与可能
- AI 分類の対象候補は、作業タグが付いていない active メール
- 利用者が作業タグを外した場合、再分類対象になり得る
- 誤分類は利用者が IMAP タグを付け替えて修正できる
- AI への入力候補は Subject と本文先頭部分

以下は未決定とする。

- 使用する AI / モデル
- AI 分類の実行タイミング
- 自動適用か確認後適用か
- AI 応答形式
- 本文を何文字・何バイト渡すか
- 分類不能時の扱い
- 信頼度を保持するか

AI 分類の詳細仕様が確定するまでは、Codex に独自判断で実装させない。

---

## 11. Version 0.2 の対象外

以下は Version 0.2 の必須実装対象外とする。

- 複数 mailbox 対応
- 複数アカウント対応
- UIDVALIDITY 変更時の高度な復旧
- UID 変更時の高度な再同定
- 追跡状態の履歴保存
- inactive メールの物理削除
- SQLite 消失時の完全復元
- 高度な同期排他制御
- React / Vue 等による SPA
- AI 分類の未確定仕様

---

## 12. 実装上の原則

Version 0.2 は将来機能を先回りして複雑化せず、現在必要な同期・状態管理・表示を単純な構造で確実に実装する。

将来必要になる可能性だけを理由に、Version 0.2 のデータモデル、同期処理、フロントエンド構成へ過剰な状態・履歴・復旧機構や UI フレームワークを追加しない。
