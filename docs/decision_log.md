正式仕様へ統合済みの Decision も履歴として残す。正式な現行仕様は `docs/design.md` を優先する。

## 2026-08-16

### Decision 001: 専用ワークフローの終了原則

- 専用ワークフローを進める主体は WIB とする。
- 専用ワークフローは利用者が「完了」または「非該当として解除」のいずれかを行って終了する。
- 専用ワークフローに属するメールのやり取りは WIB を起点として行う。
- 専用ワークフロー中のメール閲覧は WIB で行い、メール本文の作成・送信そのものは Thunderbird の機能を利用する。
- WIB が専用ワークフローの文脈を保持することで、完了時のお礼メール等を通常の `返信待ち` にしない決定的処理を可能にする。

統合先: `docs/design.md` の「基本方針」「専用ワークフロータグ」「締切登録支援」「スケジュール調整支援」。

### Decision 002: 通常ワークフローの共通終了

- `返信必要` / `見る・検討` / `注目` は通常ワークフローとする。
- 通常ワークフローは Thunderbird でメールを閲覧・処理する。
- 利用者が通常ワークフローを終了する場合は、元の通常ワークフロータグを残す。
- 終了時は `一括処理` を付け、スターを外す。
- この共通終了操作は Thunderbird Extension から 1 操作で実行できる形を目指す。
- `見る・検討` を Record として保存する場合は別経路とし、`一括処理` を付けず、`見る・検討` を残したままスターを外す。

統合先: `docs/design.md` の「通常ワークフロータグ」「Record（WIB 保存情報）」。

### Decision 003: `対応あり` を追加する

- `対応待ち` は専用ワークフローで支援者の作業結果を待つ状態とする。
- `対応待ち` の依頼メールに支援者から返信が来た場合、新着メールには `対応あり + ★` を付ける。
- `対応あり` は TriageBox が relation から決定的に付与する専用ワークフロー状態であり、通常の AI 再判定対象にしない。
- 旧依頼メールは `対応待ち` を履歴として残しつつ `一括処理 + ☆` とする。

未確定: `対応あり` の IMAP keyword と UI 細部は実装時に決める。

統合先: `docs/design.md` の「待機・専用ワークフロー状態タグ」「TriageBox の判定原則」「スケジュール調整支援」。

### Decision 004: TriageBox と TrackingBox の判定順序

- TriageBox は INBOX の未読メールを対象とし、TrackingBox より先に動作する。
- TriageBox はヘッダー、relation、送受信事実等から決定的な判断を行う。
- TrackingBox はスター付きメールについて本文の意味を AI で判定する。
- 利用者が Thunderbird でメールを確認してスターを付ける場合は原則 `既読 + ★` となり、初期 AI 判定の入口になる。
- TriageBox が relation により新着へ着眼点を移した場合は原則 `未読 + ★` となり、TriageBox が意味を確定していない限り TrackingBox の再判定候補になる。
- 旧メールの通常ワークフロータグを新着へそのままコピーしない。
- `返信待ち` への返信は TriageBox が `返信必要 + ★` と確定する。
- `対応待ち` への返信は TriageBox が `対応あり + ★` と確定する。
- 上記の決定的状態は通常の AI 再判定対象から除外する。

統合先: `docs/design.md` の「スターと着眼点」「TrackingBox」「TriageBox の判定原則」。

### Decision 005: AI 判定前の本文前処理

- AI 判定ではメール本文を単純に先頭 X 文字で切らない。
- 先に引用された過去メール部分を機械的に除去する。
- 可能な範囲で今回新たに記述された本文を抽出した後、文字数上限を適用する。
- 典型的な引用記号、返信区切り、Original Message 等を対象とし、署名も可能な範囲で除去してよい。
- 引用除去が完全であることは前提にしない。

未確定: 具体的な引用除去アルゴリズムと文字数上限は実装時に決める。

統合先: `docs/design.md` の「TrackingBox / AI に渡す本文」。

### Decision 006: 専用ワークフローの起点と現在着眼点を分ける

- 専用ワークフローは起点メールの Message-ID (`workflow_origin_message_id`) を保持する。
- 起点メールの標準メールスレッド上で着眼点が移動した場合は `current_focus_message_id` を更新する。
- 支援者への依頼メール M2 と、その返信 M3 は M1 の標準メールスレッドではないため、M3 到着で `current_focus_message_id` を M3 へ移さない。
- M1 の標準メールスレッドに継続メール M4 が来た場合は `current_focus_message_id = M4` とできる。
- 専用ワークフローで M1 から新規作成した M2 には `X-WorkInBox-Origin-Message-ID` を付け、M1/M2 の Message-ID relation を SQLite に保存する。
- M3 以降は `In-Reply-To` / `References` と SQLite relation で M1 の専用ワークフローへ到達する。

統合先: `docs/design.md` の「スターと着眼点」「スケジュール調整支援」「専用ワークフローのメール relation」。

### Decision 007: WIB ダッシュボードを仕事の出発点にする

- 利用者は原則として WIB ダッシュボードから仕事を始める。
- ダッシュボードに「スターなし未読メール数」を表示する。
- ダッシュボードに「スターなし・WIB 作業タグなし既読メール数」を表示する。
- これらから Thunderbird の対象メールへ進み、利用者が新たに着眼するメールへスターを付ける。
- 専用ワークフローは WIB で進め、通常ワークフローは Thunderbird で処理する。
- スケジュール調整の支援者依頼スレッド (`対応待ち` / `対応あり`) も WIB 内の仕事として扱う。

未確定: ダッシュボードの最終レイアウト、表示順、優先順位表現は実装時に決める。

統合先: `docs/design.md` の「利用者フロー」「ダッシュボード」。

### Decision 008: 現行タグの IMAP keyword を確定する

- `注目` の IMAP keyword は `wib-watch` とする。
- `対応あり` の IMAP keyword は `wib-action-ready` とする。
- `一括処理` は正式設計どおり `wib-bulk` を使用する。
- 旧 `wib-important` は `注目` へ自動変換しない。旧 `重要` と `注目` は意味が異なるためである。
- 旧 `wib-batch` は新規書き込みには使用しないが、既存メールを壊さないため WorkInBox 本体では `wib-bulk` として読み取る互換性を残す。
- Thunderbird Extension の現行タグ登録は13タグとし、旧 `wib-important` / `wib-batch` のローカルタグ定義を整理しても、メール上の既存 IMAP keyword は破壊的に削除しない。

未確定: 旧 keyword をメール全体から物理移行する処理は、必要性が確認できるまで行わない。

統合先: `docs/design.md` の「タグ体系」。現時点では実装時決定としていた keyword をこの Decision で確定する。

## 2026-08-17

### Decision 009: 締切候補0件は利用者が明示終了する

- AI が締切候補を0件としたことだけでは、締切登録支援を自動終了しない。
- 候補0件でも `締切あり + ★` を維持し、利用者が本文を確認する。
- 締切がある場合は利用者が候補を手動追加する。
- 締切がない場合は利用者が WIB で `締切なしとして終了` を明示的に実行する。
- `締切なしとして終了` は候補が0件の場合だけ許可する。候補が存在する場合は候補ごとに登録 / 登録しないを判断する。
- 明示終了時は `締切あり` を解除し、その後 `docs/design.md` の専用ワークフロー終了時の共通遷移を適用する。

未統合 Decision。現行の実装詳細は `docs/deadline_workflow.md` に記録する。

## 2026-08-23

### Decision 010: 既存メール振り分けは暫定接続後にWIBへ移行する

- 利用者の既存Thunderbirdメッセージフィルターによる「まとめて確認するメール」の分類は、実機テスト中も維持する。
- 暫定運用では、既存分類タグをWIBの `一括処理` へ変換する後段フィルターをThunderbirdに置く。
- 個人環境固有のタグ名、送信者、件名、ゲートウェイヘッダー条件をWIB本体へハードコードしない。
- 将来、送信者・件名・メールゲートウェイ判定等による決定論的な事前分類をWIB側へ移し、Thunderbirdの暫定変換フィルターを不要にする。

未確定: WIB側の設定形式、TriageBoxとの責務境界、既存ルールの移行方法、利用者がルールを編集するUIは実装前に決める。

### Decision 011: ダッシュボードの未着眼件数だけを直近期間に限定する

- ダッシュボードの `未着眼・未読` / `未着眼・既読` 件数は、`imap.new_mail_lookback_days` で指定した直近期間に限定する。
- 通常ワークフロー、専用ワークフロー、待機状態、Record の件数にはこの期間制限を適用しない。
- Thunderbird の未着眼 custom Mail View には期間条件を追加せず、受信箱全体を表示する現行動作を維持する。
- このため、ダッシュボード件数とThunderbirdで開いた一覧件数が一致しない場合があることを画面上に明記する。

未確定: Thunderbird側にも期間指定ビューが必要かは、実運用上の必要性を確認してから判断する。

### Decision 012: メール全体を締切なしとして一括終了できる

- AIが締切候補を誤検出した場合、候補ごとの操作を繰り返さず、メール全体を `締切なし` と一度で判断できる。
- この操作は未確定候補をすべて `登録しない` にし、`締切あり` を外して専用ワークフローを終了する。
- すでに正式登録済みの締切が存在する場合は、登録済みデータの意図しない取消しを避けるため利用できない。

Decision 009 の「候補0件の場合だけ許可する」という制限を、このDecisionで置き換える。

### Decision 013: 専用ワークフロー件数は詳細画面と同じactiveメールを数える

- ダッシュボードの `締切あり` / `スケジュール調整` 件数は、IMAP受信箱全体ではなくWIBのSQLiteに存在するactiveメールのうち、該当するlive IMAPタグを持つものを数える。
- 締切・スケジュール詳細画面と同じ母集団にすることで、ダッシュボード件数から詳細へ進んだ際の不一致を防ぐ。
- WIBへ未取り込みの古いタグ付きメールは、専用ワークフロー件数へ含めない。

### Decision 014: Thunderbirdから通常ワークフローを1クリックで終了する

- Thunderbirdで表示中の通常ワークフローメールに、Extensionの終了ボタンを提供する。
- 1回の操作で既存タグを保持して `一括処理` を追加し、スターを外す。
- `返信必要` / `見る・検討` / `注目` のいずれもないメールでは動作させず、専用ワークフロー等の誤終了を防ぐ。
- Record保存終了はSQLiteへの入力が必要なため、このボタンの対象に含めない。

## 2026-08-25

### Decision 015: VTODOから締切の元メールへ1クリックで戻る

- WIBが生成する各VTODOの主URLに、Thunderbirdが標準対応する `mid:` URIを付け、Message-IDから元メールを直接表示する。
- VTODOの説明欄には、締切IDを含むWIBの元メール案内URLも付ける。
- 案内URLを外部ブラウザで開いた場合やBridge連携に失敗した場合は、締切・件名・差出人・受信日時の最低限の情報をWIBで表示する。
- SQLiteを締切の正本、VTODOを読み取り専用の派生表現とする現行設計は変更しない。

## 2026-08-30

### Decision 016: Thunderbird通常作業はWIB停止中も継続できる

- Thunderbird Extension内に専用ダッシュボードタブを設ける。
- 未着眼、通常ワークフロー、専用タグ、待機タグの作業件数はThunderbirdが保持するメッセージの既読・スター・タグから計算する。
- `new_mail_lookback_days` は既存設計どおり未着眼・未読 / 未着眼・既読の件数だけに適用する。
- WIB停止中もThunderbirdの作業ビュー、閲覧、返信、スター、タグ、通常終了を利用できる。
- AI、SQLite、relation、Record、専用ワークフローの状態更新はWIB接続中だけ利用できる。
- ExtensionはWIBのhealth APIで接続状態を表示し、接続設定と直近の集計結果だけをローカル保存する。credentialとメール本文は保存しない。
- 現在のWIB Web UIは維持し、全画面移植やオフライン更新キューは初回実装に含めない。

統合先: `docs/design.md` の「システム構成」「利用者フロー」「Thunderbirdの役割」。詳細は `docs/thunderbird_bridge.md` と `docs/extension_dashboard_proposal.md`。

### Decision 017: ダッシュボードの未着眼作業ビューも直近期間に限定する

- ダッシュボードの `未着眼・未読` / `未着眼・既読` から開くThunderbird作業ビューには、件数と同じ `imap.new_mail_lookback_days` を適用する。
- 通常ワークフロー、専用ワークフロー、判定保留、待機状態の作業ビューはmailbox全体を対象とする。
- WIB Web側など保存済み日数を持たない導線から未着眼ビューを開く場合は、従来どおりmailbox全体を対象にする。

Decision 011 の「未着眼custom Mail Viewには期間条件を追加しない」という判断を、実機確認で判明した使いにくさに基づいてこのDecisionで置き換える。

### Decision 018: 未着眼は未読・既読を1カードと1作業ビューにまとめる

- WIB WebとExtensionダッシュボードは、未着眼の合計件数と「うち未読 / 既読」の内訳を1カードに表示する。
- 未着眼カードから開くThunderbird作業ビューは未読・既読を分けず、`new_mail_lookback_days`内の未着眼メールをまとめて表示する。
- WIB Web側もExtension bootstrapから日数を取得して渡し、WIB WebとExtensionダッシュボードの導線を同じ条件にする。
- 既存の未着眼・未読 / 未着眼・既読の内部ビュー名とpopup選択肢は互換性のため残す。

Decision 017 の2カード構成を、実運用で切り替え操作が有効に働かないことと、一覧を一緒に確認したい要望に基づいてこのDecisionで置き換える。

### Decision 019: Extensionダッシュボードから通常同期を開始できる

- 接続状態欄に通常同期ボタンを置き、WIB接続中だけ有効にする。
- Extensionは`POST /api/sync`で既存のバックグラウンド同期を開始し、`/api/sync-status`で実行状態を追跡する。
- 同期実行中の二重起動とWIB接続不可時の操作をUIで防止する。
- 全件再確認は誤操作の影響が大きいため、今回のボタンには含めない。
