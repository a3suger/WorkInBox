# WorkInBox の構成と返信待ち管理

更新日: 2026-08-13

この文書は、タグ体系の再整理後に行った議論をもとに、WorkInBox の構成要素、Thunderbird との責務分担、`返信待ち` の判定・再評価・定期レビューについて現時点の合意をまとめる。

この文書は、既存の `docs/design_workflow.md`、`docs/triagebox_decision_flow.md`、`docs/schedule_reply_workflow_2026-08-12.md` を今後整合させるための設計ノートとする。

---

## 1. WorkInBox は 3 つの構成要素からなる

WorkInBox 全体は、実質的に次の 3 つの構成要素からなるものとして整理する。

1. **WIB Web UI + Thunderbird Extension**
2. **TrackingBox**
3. **TriageBox**

TrackingBox と TriageBox だけを内部処理系として見るのではなく、利用者との接点である Web UI と Thunderbird Extension も WorkInBox の主要構成要素として扱う。

### 1.1 WIB Web UI + Thunderbird Extension

利用者との接点と、Thunderbird との橋渡しを担当する。

主な役割:

- 専用ワークフローの画面表示と利用者操作。
- `判定保留` や `返信待ち` など、利用者判断が必要な状態の表示・変更。
- `返信待ち` の優先順位表示と定期レビュー。
- WIB から Thunderbird の対象メールを開く。
- Thunderbird 側で必要な Quick Filter 作業ビューを開く。
- WIB が意味を知っている送信メールへ、必要に応じて relation や用途を示す拡張ヘッダーを付ける。

Web UI はメール本文を編集・送信する独自メールクライアントにはしない。

### 1.2 TrackingBox

主に、現在注目しているメールについて **意味を解釈し、整理する** 役割を担当する。

主な役割:

- 初期ワークフロータグの AI 判定。
- `判定保留` の整理支援。
- 専用ワークフロー開始支援。
- 送信後に `返信待ち` とされたメールについて、本当に返信を業務上待つ必要があるかを AI で再判定する。
- `返信待ち` メールを定期的に再評価する。
- `返信待ち` の優先順位を計算し、WIB 上で見やすい順に提示する。

TrackingBox は、単にタグを付けるだけでなく、**現在注目すべきメールの意味と順番を整理する**ものとする。

### 1.3 TriageBox

主に、新しく観測したメールについて **事実・関係・決定的な状態遷移** を扱う。

主な役割:

- 未読メールの取り込み。
- 自分が送信したメールの検出。
- 返信メールの検出。
- `In-Reply-To` / `References` / relation による前後関係の確認。
- `返信待ち` / `対応待ち` への返信検出。
- 着眼点を旧メールから新メールへ移す。
- 旧着眼点への `一括処理` 付与とスター解除など、relation から決定できる状態遷移。

基本的な責務分担は次のように考える。

```text
TriageBox
  = 事実・関係・決定的な状態遷移

TrackingBox
  = 意味・分類・優先順位・再評価

Web UI + Thunderbird Extension
  = 利用者判断・ワークフロー操作・Thunderbird との接続
```

## 2. Thunderbird はメール実行環境のままとする

メール本文を書く、返信する、送信する、といったメール操作は Thunderbird の機能を使う。

WIB Web にメール作成・返信本文編集の機能を重複実装しない。

利用者が WIB で「返信する」「催促する」などの判断をした場合も、基本的には次の流れとする。

```text
WIB で対象と次の行動を判断
        ↓
WIB から Thunderbird で対象メールを開く
        ↓
利用者が元メール・文脈を確認
        ↓
Thunderbird の返信ボタンを押す
        ↓
Thunderbird の標準機能で本文作成・宛先確認・添付・送信
```

つまり、

> Thunderbird = メール業務の実行環境
>
> WIB = メールから発生する仕事の判断・整理・進行管理環境

という既存の基本原則を維持する。

## 3. WIB から Thunderbird で対象メールを開く機能を共通基盤にする

今後、複数のワークフローから「元メールを開いて Thunderbird で処理する」導線を使う。

代表例:

- `返信必要` のメールへ返信する。
- `返信待ち` メールについて催促する。
- 締切作業の完了後、回答が必要な元メールへ戻る。
- スケジュール調整完了後、`返信必要` の元メールへ戻る。
- WIB 上で内容を確認した後、元メールのスレッドや添付を Thunderbird で確認する。

そのため、**WIB から Thunderbird で対象メールを開く機能は個別ワークフローの付属機能ではなく共通基盤として設計する。**

目標とする動作:

1. WIB が Message-ID 等の安定した識別情報を Thunderbird Extension へ渡す。
2. Extension が対象 account / mailbox を正しく解決する。
3. Thunderbird 内で対象メールを高速に発見する。
4. 対象メールが入っているメールタブまたは適切な表示を開く。
5. 対象メールを選択して本文を表示する。
6. 利用者はその状態から Thunderbird 標準の返信・転送等を行う。

検索結果一覧を出して利用者にもう一度探させるのではなく、可能な限り **対象メールそのものを直接開く** UX を目標とする。

従来検討していた「Thunderbird 元メール検索高速化」は、単なる性能改善ではなく、この WIB → Thunderbird 導線の中核機能として扱う。

## 4. `返信待ち` の意味

`返信待ち` は単に「自分が送ったメール」を表すタグではない。

次の意味とする。

> **相手からの次のアクションを業務上待っている送信メール。**

自分が送ったメールには、少なくとも次の種類がある。

1. 相手からの返答を業務上待つ必要がある。
2. 返答が来る可能性はあるが、追跡する必要はない。
3. 明らかに返信不要である。

たとえば、スケジュール支援を終了するときに支援者へ送る単純なお礼メールは、通常 3 に相当する。

## 5. 送信直後の `返信待ち` 判定

通常の送信メールについて、送信直後に `返信待ち` の要否を自動判定する。

基本方針:

```text
送信メールを検出
      ↓
必要なら暫定的に返信待ち候補とする
      ↓
TrackingBox が AI で
「相手からの返信を業務上待つ必要があるか」を判定
      ↓
Yes: 返信待ち + ★ を維持
No : 返信待ちの追跡対象から外し、整理対象へ
```

AI には複雑な案件分類をさせるのではなく、送信メールについて次の狭い問いを判定させる。

> このメールについて、相手からの返信・確認・作業結果を業務上待つ必要があるか。

見逃しを避けるため、AI が迷う場合は `返信待ち` 側へ倒す。

### WIB が意味を知っている送信メール

WIB 自身が用途を確定できる送信メールは AI に任せない。

例:

- スケジュール支援終了時のお礼メール。
- 将来追加される、明示的に返信不要と分かる WIB 生成メール。

このようなメールには Thunderbird Extension が relation / 用途 / 返信不要等を示す拡張ヘッダーを付与し、TriageBox が決定的に後処理できるようにする案を採用する。

拡張ヘッダーの具体的な名称と形式は未決定とする。

## 6. `返信待ち` は WIB の処理対象とする

`返信待ち` は Thunderbird Quick Filter で見るだけではなく、WIB Web の管理対象とする。

WIB の `返信待ち` 画面では、少なくとも次を行えるようにする方向で設計する。

- `返信待ち` の一覧を見る。
- TrackingBox が算出した優先順位を見る。
- AI の「返信を待つ必要がある / ない」という判断を利用者が修正する。
- 「もう待たなくてよい」と利用者が終了判断する。
- 催促や再連絡が必要なメールを選ぶ。
- 対象メールを Thunderbird で開く。

メール本文の作成は WIB 内では行わない。

催促する場合も、WIB で対象を選択した後、Thunderbird で元の送信メールを開き、利用者が内容を確認して Thunderbird 標準の返信機能を使う。

Thunderbird の `WIB:返信待ち` Quick Filter は **メールそのものを見る場所**、WIB Web の `返信待ち` 画面は **どの返信待ちを今気にすべきか判断・整理する場所** と位置付ける。

## 7. `返信待ち` の定期レビューと優先順位

送信直後の自動判定とは別に、利用者は `返信待ち` を定期的にレビューする。

`返信待ち` が増えた場合、単純な日付順だけでは重要な待ち状態を見落とす可能性があるため、TrackingBox が優先順位を算出して WIB 上で並べ替える。

優先順位は新しい IMAP タグとして固定せず、その時点の状況から計算する動的な値とする。

理由:

- 昨日は低優先でも、期限が近づけば高優先になる。
- 返信がない期間が長くなれば優先度が変わる。
- 関連締切の状況によって優先度が変わる。

優先順位の材料候補:

- 送信してからの経過日数。
- 本文または relation 上に明示的な期限があるか。
- 関連する正式締切までの残り時間。
- 相手に明示的な回答・確認・作業を依頼しているか。
- 相手から返事がないと次の作業が止まるか。
- 元メールまたは関連メールに `重要` が付いているか。
- 以前に催促を行っているか。
- AI が本文から推定する業務上の重要度。

決定的な条件を先に利用し、AI は補助的に使う方向が望ましい。

例:

```text
期限超過 / 期限直前
    ↓
優先度を大きく上げる

長期間返信なし
    ↓
優先度を上げる

その他
    ↓
AI が内容から優先度を補正
```

WIB の表示例:

```text
返信待ち

要確認
1. ○○先生：申請書の確認依頼
   4日前 / 締切まで2日

2. △△社：見積回答待ち
   6日前

通常
3. ...
4. ...
```

具体的なスコアリング方式・閾値・表示グループは実装設計時に決定する。

## 8. 専用ワークフローと Thunderbird の関係

`締切あり` と `スケジュール調整` の専用ワークフローは WIB で進める。

WIB が管理するもの:

- 現在の専用ワークフロー状態。
- 利用者に必要な選択肢。
- AI 抽出・AI 判断の確認と修正。
- ワークフロー完了の確定。
- 次に Thunderbird で処理すべき元メールへの導線。

Thunderbird が担当するもの:

- 元メールを読む。
- 添付やスレッドを確認する。
- 返信・依頼・催促等のメール本文を書く。
- 宛先・Cc・添付等を調整する。
- メールを送信する。
- 最終的にメールをアーカイブする。

この分担により、WIB は独自メールクライアント化せず、Thunderbird の既存機能を最大限利用する。
