### 対応ありメールに対する3種類の操作（決定事項）

支援者からの返信M3が`対応あり + スターあり`になった後の操作として、メール閲覧画面のWIB操作メニューへ次の3項目を追加する。

1. `追加の質問を送る`
   - M3への返信作成画面を開く。
   - Extensionは、作成画面を開いた時点でも送信成功後でもM3のタグとスターを変更しない。
   - TrackingBoxが追加質問M5とM3のrelationを検出し、M3を既存タグを維持したまま`一括処理 + スターなし`、M5を`対応待ち + スターあり`にして着目点を移す。
2. `お礼を送って終了`
   - M3への返信作成画面を開く。
   - 利用者が編集後に送信し、送信が正常終了した場合だけ、ExtensionがM3へ`一括処理`を追加する。M3のスターと既存タグはこの時点では変更しない。
   - `一括処理 + スターあり`を、お礼送信済みでTrackingBoxの終了処理を待つ中間状態として扱う。
   - TrackingBoxはお礼M5とM3のrelation、およびM3の`一括処理`を確認して追加質問と区別し、M3のスターを外す。M5も`一括処理 + スターなし`として終了させ、新しい`対応待ち`にはしない。
3. `返信せず終了`
   - 返信作成画面は開かない。
   - ExtensionがM3へ`一括処理`を追加し、スターを外して終了させる。既存タグは維持する。

返信作成画面を開いただけの場合、下書きを破棄した場合、送信に失敗した場合はM3を変更しない。複数の作成画面を同時に開いても取り違えないよう、Extensionは作成タブごとに元のM3のThunderbird内部メッセージIDと操作種別を対応付ける。TrackingBoxはスターありを処理対象とするため、`一括処理 + スターあり`も除外せず処理する。再実行時にも同じ最終状態へ収束するよう処理を冪等にする。

### WIB操作メニューの表示と通常フロー（決定事項）

- `対応あり`タグが付いたメールでは、通常フロー、専用フロー、通常終了、Record終了を表示しない。上記の「追加の質問を送る」「お礼を送って終了」「返信せず終了」の3項目だけを表示して選択可能にする。
- `対応あり`タグがないメールでは、対応ありメール用の3項目を表示せず、通常フロー、専用フロー、終了操作を表示する。
- 通常フローは`回答必要`・`見る・検討する`・`注目`の3項目から1つを選ぶチェック式メニューとする。現在のタグに対応する項目へチェックを表示する。
- 通常フローの3タグは排他的に扱う。別の項目を選び直した場合は、以前の通常フロータグを外し、選択したタグだけが1つ付いた状態にする。通常フロータグを履歴として残さない。
- 終了操作には`通常終了`と`Recordに記録して終了`の両方を表示し、どちらも選択できるようにする。
- 専用フローの表示と動作は、Extension `0.3.18`までに決定・実装した内容を維持する。

これにより、WIB操作メニューの内容、表示条件、各項目の基本動作は決定済みとなった。専用フロー部分は実装済みであり、通常フロー、終了操作、対応ありメール用の3操作が次の実装対象である。

### Recordに記録して終了（決定事項）

- `Recordに記録して終了`を選ぶと、Extensionが自分宛てのRecord登録依頼メールの作成画面を開く。
- メールの件名をRecordの必須タイトル、本文を任意の補足情報として使用する。
- 登録依頼メールには、少なくともRecord登録依頼であることを示す種別、元メールのMessage-ID、重複登録防止用の一意な依頼IDを特殊ヘッダーとして付ける。ヘッダー名の具体値は実装時に既存のWIB関連ヘッダーと整合させる。
- 作成画面を開いただけの場合、下書きを破棄した場合、送信に失敗した場合は元メールを変更しない。
- 登録依頼メールの送信が正常終了した場合だけ、Extensionが元メールへ`一括処理`を追加する。スターと既存タグは維持し、`一括処理 + スターあり`をRecord自動処理待ちの中間状態とする。
- TriageBoxは特殊ヘッダー付きの登録依頼メールを検出し、件名・本文・元メールのMessage-ID・依頼IDをSQLiteのRecordへ保存する。依頼IDによって同じ依頼の二重登録を防ぐ。
- TrackingBoxは元メールをAIで要約し、その情報をRecordへ追加保存する。一連の処理が成功した後、元メールのスターを外して`一括処理 + スターなし`へ進める。登録依頼メールも通常の着眼対象にせず、`一括処理 + スターなし`にする。
- Record登録またはAI要約に失敗した場合は元メールのスターを残し、後続同期で安全に再実行できるよう処理を冪等にする。
- お礼メール送信後の中間状態も`一括処理 + スターあり`だが、Record登録依頼は特殊ヘッダーで識別するため、TrackingBoxは両者を区別できる。
- Recordの一覧と詳細の閲覧はWIB Webの責務とし、Thunderbird Extension内にはRecord閲覧画面を作らない。Recordには元メールのMessage-IDを保持し、WIB Webから既存の元メール導線を利用できるようにする。
- Recordの編集、削除、検索条件等の追加機能は今回の基本仕様には含めず、必要になった時点で別途決定する。
