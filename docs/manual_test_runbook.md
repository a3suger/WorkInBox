# WorkInBox 実機テスト再開手順

この文書は、WorkInBox の実機テストを中断後に再開するときの入口である。

**再開時は、まずこの文書だけを上から順に読む。** Issue #17〜#25 や詳細設計は、問題が起きた場合にだけ参照する。この文書にパスワード、アクセストークン、メール本文などの機密情報を書かない。

## 1. テスト環境の前提

端末名、個人用パス、SSH構成などは公開文書へ書かず、Git管理外の非公開引き継ぎメモを正本とする。

| 項目 | 値 |
| --- | --- |
| WIB実行端末 | WIB Web、SQLite、Ollamaを実行する端末 |
| テスト操作端末 | Thunderbirdとブラウザを実行する端末 |
| Thunderbird | 140以上（実バージョン: **未記入**） |
| Thunderbirdプロファイル | **未記入** |
| 対象IMAP | `config.yaml` と一致するアカウント（アドレスは記載しない） |
| 対象mailbox | 通常 `INBOX`（実設定: **未記入**） |
| リポジトリ | 各端末の絶対パスは非公開メモに記載する |
| ブランチ | `main` |
| Python | 3.14以上（実バージョン: **未記入**） |
| 仮想環境 | WIB実行端末のリポジトリ内 `.venv` |
| 設定 | WIB実行端末のリポジトリ内 `config.yaml`（Git管理外） |
| SQLite | `config.yaml` の `database.path`（通常 `data/workinbox.db`） |
| Ollama | `http://127.0.0.1:11434`。モデルは `config.yaml` を正本とする |
| WIB Web | テスト操作端末から `http://127.0.0.1:8000/` で開ける状態にする |
| Extension | テスト操作端末の `thunderbird/workinbox-extension/manifest.json` |
| タグ定義バックアップ | Extension外の安全な場所に保管する |

## 2. 再開前の安全確認

- [ ] 正しいThunderbirdプロファイルとIMAPアカウントを開いている
- [ ] WIB実行端末とテスト操作端末が利用できる
- [ ] 非公開メモに定めた接続経路が有効である
- [ ] `config.yaml` の `imap.host` / `port` / `username` / `mailbox` が対象アカウントと一致する
- [ ] `config.yaml` と `data/` がGit管理外である
- [ ] Thunderbirdタグの導入前バックアップJSONが残っている
- [ ] 既存のThunderbirdメッセージフィルターとWIBタグの関係を確認している
- [ ] 人工的なメールを作らず、通常の受信箱と実際の業務メールを使う
- [ ] Message-ID、UID、本文、メールアドレスを公開Issueへ書かない

タグを新規導入する端末では、先にExtensionから「導入前スナップショットを保存」と「JSONを書き出す」を実行する。導入済みなら既存バックアップを上書きしない。

既存フィルターがWIB以外のタグで「一括確認するメール」を分類している場合、そのタグだけではWIBの未着眼対象から除外されない。従来タグがすべて一括確認の意味なら、既存フィルターは変更せず、従来タグをWIBの `一括処理` へ変換する後段フィルターを1つ追加する。

### 既存メッセージフィルターをWIBへ接続する

個別のフィルター名・条件・アカウント情報は非公開メモを正本とする。

1. ThunderbirdでWIBの `一括処理` タグが登録済みであることを確認する。
2. 既存フィルターの設定と順序をスクリーンショット等で保存する。
3. 従来タグを付ける既存フィルターは変更しない。
4. 既存フィルターより後ろに、従来タグ付きメールへWIBの `一括処理` を付ける変換フィルターを追加する。
5. 変換フィルターを手動実行可能かつ新着受信時に実行する設定にする。
6. まず新着1件で、従来タグとWIBの `一括処理` が両方付くことを確認する。
7. 問題がなければ、変換フィルターだけをINBOXへ手動実行する。
8. 従来タグ付きの既存メールに `一括処理` が追加され、スターや既読状態が変わっていないことを確認する。

フィルター変更後に大量の想定外メールへ `一括処理` が付いた場合は、#24・#25へ進まず停止する。

## 3. コードと環境を最新化する

WIB実行端末とテスト操作端末に別々のリポジトリがある場合は、両方を同じcommitへ合わせる。

```bash
git status -sb
git pull --ff-only
git log --oneline --decorate -n 5
source .venv/bin/activate
python --version
python -m pip install -e .
python -m unittest discover -s tests -v
```

Python環境の更新と自動テストはWIB実行端末で行う。

両端末の `git log -1 --oneline` が同じcommitを示すことを確認する。未commit変更があれば、内容を確認せずにpull、破棄、上書きをしない。テストが失敗した場合は実機確認へ進まず、失敗したテスト名とエラーを記録する。

## 4. WorkInBoxを起動する

Ollamaを起動し、`config.yaml` のモデルを利用できることを確認する。続いてリポジトリ直下で実行する。

```bash
source .venv/bin/activate
workinbox-web --config config.yaml
```

WIB Webのターミナルを閉じない。非公開メモに定めた接続を開始し、テスト操作端末で `http://127.0.0.1:8000/` を開く。

- [ ] ダッシュボードがエラーなく表示される
- [ ] `/api/thunderbird/imap-target` が対象IMAP設定を返し、passwordは返さない
- [ ] WIB Webターミナルにテスト操作端末からのアクセスが記録される

必要なときだけ通常同期を1回実行する。同期ボタンを繰り返し押さない。全件再確認はinactiveメールも再確認する必要がある場合だけ使う。

同期中は画面上部で、現在の段階、処理済み件数 / 対象件数、エラー件数を確認する。主な表示は次のとおり。

- `TriageBox: 未読メール取得`
- `TriageBox: 未読メール確認`
- `TrackingBox: 既存active確認`
- `TrackingBox: 新着スター付き取り込み`
- `TrackingBox: AI分類対象確認`
- `TrackingBox: AI初期分類`

件数が長時間変化しない場合は同期ボタンを押し直さず、表示中の段階と件数を記録する。

## 5. Thunderbird Extensionを読み込む

1. Thunderbirdの「Add-ons Debugging」を開く。
2. 「Load Temporary Add-on...」を選ぶ。
3. テスト操作端末のリポジトリにある `thunderbird/workinbox-extension/manifest.json` を選ぶ。
4. リポジトリ更新後は、読み込み済みでもTemporary Add-on自体をReloadする。
5. ツールバーのWorkInBoxボタンから「WorkInBoxを開く」を押す。

Extensionエラーが出たら続行せず、エラー全文、操作したビュー、Thunderbirdバージョンを記録する。

## 6. 実機テスト順

Issue番号順ではなく、同じ環境・メールを再利用できる次の順で行う。

### A. ダッシュボードと作業ビュー（#24・#25）

ダッシュボード:

- [ ] `/` がダッシュボードになっている
- [ ] `未着眼・未読` が「スターなし + 未読 + 一括処理なし」と一致する
- [ ] `未着眼・既読` が「スターなし + 既読 + 一括処理なし」と一致する
- [ ] 返信必要、見る・検討、注目の件数が実際の状態と一致する
- [ ] 締切、スケジュール調整、判定保留、待機・対応あり、Recordへ移動できる

旧 `wib-batch` も一括処理済みとして未着眼から除外する。

Thunderbird:

- [ ] `未着眼・未読` で `WIB 未着眼` と未読Quick Filterが有効になる
- [ ] スターを付けると未着眼一覧から外れる
- [ ] `未着眼・既読` で未読Quick Filterが外れる
- [ ] `返信必要` は `wib-answer + ★` だけを表示する
- [ ] `見る・検討` は `wib-review + ★` だけを表示する
- [ ] `注目` は `wib-watch + ★` だけを表示する
- [ ] 未着眼から通常ワークフローへ切り替えると未着眼Mail Viewが解除される
- [ ] 同じWIB専用タブを再利用し、設定どおりのアカウントとmailboxを開く

### B. AI分類、通常終了、Record、締切（#17・#22・#23）

条件に合う実メールが届いたときに行う。一度に全ケースを揃えなくてよい。

AI初期分類:

- [ ] 期限と通常作業の両方があるメールで専用タグと通常タグが共存する
- [ ] `見る・検討` と `注目` が自然に選ばれる代表例を確認する
- [ ] `何もしなくてよい` かつ専用ワークフローなしで `一括処理 + ☆` になる

通常終了:

- [x] 元の通常タグが残り、`一括処理` が付き、スターが外れてactive一覧から外れる
- [x] ThunderbirdのWIB終了ボタン1回でも同じ遷移になる
- [ ] 通常タグのないメールではWIB終了ボタンを押しても変更されない

Record保存終了:

- [ ] RecordがSQLiteへ保存され `/records` に表示される
- [ ] RecordからThunderbirdの元メールを開ける
- [x] Thunderbird内のWIBで元メールリンクを押すと、`mid:`により待たずに元メールが開く
- [x] 「見つからない場合は検索」で従来検索を実行できる
- [ ] 元の通常タグが残り、`一括処理` は付かず、スターが外れる

締切登録支援:

- [x] 候補があれば登録、修正、登録しないを選べる
- [x] 1件以上登録し全候補を判断すると `締切登録済み` が付く
- [x] 全候補を登録しなければ `締切あり` が外れ、完了タグは付かない
- [x] 候補0件では自動終了せず `締切あり + ★` を維持する
- [x] 候補の有無にかかわらず `このメールには締切なしとして終了` を一度実行すると、未確定候補がすべて却下され `締切あり` が外れる
- [x] 他作業がなければ `一括処理 + ☆`、あればそのワークフローを継続する
- [x] 正式締切からThunderbirdの元メールを開ける
- [ ] `締切登録済み`のメールが、WIB WebとExtensionの件数および「Thunderbirdで見る」の一覧に含まれない
- [x] ThunderbirdのToDo詳細に表示される「関連リンク」（VTODOの `mid:` URL）を1回クリックし、Thunderbird内で元メールが直接表示される
- [ ] 説明欄のWIB案内URLを外部ブラウザで開くと、締切・件名・差出人・受信日時が表示される
- [ ] 元メールが見つからない場合も、WIBの案内画面に情報と失敗状態が残る

限定CalDAV（#32）:

- [x] `docs/limited_caldav.md`の移行手順どおり、旧`deadlines.ics`を解除してCalDAVを登録できる
- [x] 既存ToDoが二重にならず、`mid:`関連リンクから元メールを開ける
- [x] Thunderbirdでタイトル、着手日、期限、説明、重要度を変更し、再表示後も保持される
- [x] Thunderbirdで完了・完了解除を行い、WIBの期限超過・7日以内件数へ反映される
- [x] WIB Webでタイトル、期限、説明を変更しても、着手日、完了状態、重要度が失われない
- [x] 同じToDoを古い状態から更新した場合は競合として拒否され、無条件に上書きされない

### C. スケジュール調整の一連確認（#18〜#21）

- [ ] `依頼済み`または`スケジュール対応済み`のメールが、WIB WebとExtensionの件数および「Thunderbirdで見る」の一覧に含まれない

```text
M1: 専用ワークフローの起点メール
M2: WIBから支援者へ作成・送信する新規メール
M3: 支援者からM2への返信
M4: M1の標準メールスレッドに届く継続メール
```

M1からM2送信後:

- [ ] M2はReplyではなく別スレッドになり、元メールが本文内転送として含まれる
- [ ] M2に `X-WorkInBox-Origin-Message-ID: <M1 Message-ID>` が付く
- [ ] 送信成立後、ExtensionがM1へ `依頼済み` を付ける

self-CcのM2を同期後:

- [ ] M1/M2 relationがSQLiteへ保存され、M2が `対応待ち + ★` になる
- [ ] 通常同期前にM2を開いて既読にしても、同期後に `対応待ち + ★` になる
- [ ] TriageBoxはM1の `依頼済み` を重複付与しない

M3到着・同期後:

- [ ] M2は `対応待ち` を残して `一括処理 + ☆` になる
- [ ] M3は `対応あり + ★` となり、`スケジュール調整` は付かない
- [ ] 通常同期前にM3を開いて既読にしても、同期後に `対応あり + ★` になる
- [ ] M3はAI再分類されず、標準ヘッダーとrelationからM1に結び付く
- [ ] M1は未完了の `スケジュール調整` として残る
- [ ] M1のcurrent focusはM3へ移動しない

M4到着・同期後:

- [ ] originはM1のまま、current focusがM4へ移る
- [ ] M4がスター付きの着眼対象になる
- [ ] さらに標準スレッドが続けば、前の非起点focusは `一括処理 + ☆` になる

### D. Extension内ダッシュボード（#31）

オンライン確認:

- [x] Extension popupからダッシュボードを開くとThunderbird内に専用タブが1枚だけ開く
- [x] もう一度開くと同じダッシュボードタブが再利用される
- [x] WIB接続中、最終接続成功、WIBバージョン、最終同期、同期状態が表示される
- [ ] WIB接続中にExtensionダッシュボードの通常同期を開始でき、実行中表示から完了へ戻る
- [x] 未着眼・通常ワークフロー・専用タグ・判定保留・待機状態の件数が表示される
- [ ] 未着眼が合計と未読 / 既読の内訳で表示され、WIB WebとExtensionの両方から開く作業ビューだけが`new_mail_lookback_days`の対象になる
- [x] 各カードから対応するThunderbird作業ビューを開ける
- [x] 既読、スター、タグを代表1件で変更すると件数が更新される
- [x] WIB Webが必要な各導線を開ける

オフライン・復旧確認:

- [x] WIBを停止すると30秒以内または手動更新で`WIB接続不可`になる
- [x] 接続不可でも保存済み設定からThunderbird件数を更新できる
- [x] 接続不可でも各Thunderbird作業ビューを開ける
- [x] WIB Webが必要な導線は理由付きで無効になる
- [ ] 接続不可時はExtensionダッシュボードの通常同期ボタンを押せない
- [x] WIBを再起動すると30秒以内または手動更新で`WIB接続中`へ戻る
- [x] 接続復旧後にWIB Webの導線が再び利用可能になる

## 7. 結果の記録

Issueへ次の形式で記録する。機密情報は伏せる。

```text
実施日:
WIB実行端末 / OS:
Thunderbird端末 / OS:
Thunderbirdバージョン:
WorkInBox commit:
対象ケース:
期待結果:
実際の結果:
判定: OK / NG / 未確認
補足:
```

問題がなければ完了条件を満たしたことをコメントしてCloseする。問題があればCloseせず、操作順、期待と実際のタグ・画面、Extensionエラーを記録する。

## 8. 停止条件

次の場合はその場で止め、最後に成功した操作、画面、Issue、タグ状態を記録する。

- 対象アカウントまたはmailboxに確信がない
- 予期しない多数のメールが更新されそう
- タグ定義や既存タグが消えた
- 設計にない状態遷移が必要になった
- 実メールの送信先やCcに確信がない
- DBとIMAPのどちらを修正すべきか判断できない
- 接続経路が切れ、テスト操作端末の `127.0.0.1:8000` へ接続できない

## 9. テスト終了時

- [ ] 実施したIssueへ結果を記録した
- [ ] 完了条件を満たしたIssueだけCloseした
- [ ] 問題があれば再現情報を残した
- [ ] `docs/current_work.md` の完了事項、残作業、Actions、commitを更新した
- [ ] 文書変更があれば自動テスト、commit、push、GitHub Actionsを確認した
