# WorkInBox 開発のお約束

この文書は、WorkInBox の仕様検討と実装に時間をかけ過ぎないために、利用者と開発支援側で共有する進め方を短く定める。

目的は、仕様を雑にすることではなく、**今決めるべきことだけを決め、決定を軽く記録し、実機で確かめながら前へ進むこと**である。

---

## 1. 仕様を 3 段階に分ける

仕様上の論点は、原則として次の 3 つに分類する。

### 今決める

実装を始めるために必要なもの。

例:

- 状態遷移
- TrackingBox / TriageBox / WIB Web / Thunderbird Extension の責務
- データの正本
- DB に最低限必要な項目
- 既存仕様との境界

### 実装時に決める

実装しながら選んでも手戻りが小さいもの。

例:

- ボタン配置
- タブか独立ウィンドウか
- UI の細かな表示
- 検索の最適化方法
- AI の閾値や優先順位アルゴリズムの細部

### 将来でよい

現在の利用価値や実装に直接必要でない拡張。

例:

- 高度な relation
- 汎用的な Knowledge / Record 機能
- 高度な自動化
- 将来の UI 拡張

議論中に新しい論点が出た場合は、まず「これは今決めないと実装できないか」を確認する。

今決める必要がなければ、その場で深掘りし過ぎない。

---

## 2. 設計変更はまず「決定ログ」として残す

小さな設計判断のたびに正式設計書全体を書き直さない。

まず、決まったことを短い Decision として残す。

例:

```text
Decision 023
- 通常フローに「注目」を追加する
- 継続メールへ着眼点が移った場合、通常タグをそのままコピーしない
- TriageBox は relation と着眼点移動を担当する
- TrackingBox が新しい着眼点を再分類する
```

Decision には少なくとも次を含める。

- 何を決めたか
- なぜそうしたか（必要な場合のみ）
- 何をまだ決めていないか

一定数の Decision がまとまった時点、または実装前に正式設計 `design.md` へ統合する。

正式設計へ統合済みになった Decision は、履歴として残してよい。

---

## 3. 仕様完成度 70% で実装し、実機で判断する

紙の上で 100% の仕様を完成させてから実装することを目標にしない。

状態・責務・正本・最低限のデータ構造が決まり、致命的な矛盾がなければ実装へ進む。

基本サイクルは次のとおりとする。

```text
最低限の仕様を決める
        ↓
最小実装
        ↓
GitHub Actions / 自動テスト
        ↓
Thunderbird + WIB で実機確認
        ↓
実際の操作で感じた違和感だけ修正
        ↓
必要なら Decision を追加・更新
```

特に Thunderbird と連携する UX は、設計上の想像だけで最終決定せず、可能な限り実機で判断する。

---

## 運用ルール

今後の設計相談では、可能な限り各論点を次のように整理する。

```text
今決める
実装時に決める
将来でよい
```

一度に複数の大きなテーマを完成させようとせず、1 回の議論では原則 1 つの主要テーマを決める。

仕様検討中に関連する新しいアイデアが出ても、そのテーマの実装に不要なら「実装時」または「将来」へ送る。

WorkInBox は、長く考えて完成形を当てにいくより、**小さく決め、小さく実装し、実際に使って修正する**方法を基本とする。
